# Security Boundaries

This document lists every operation that must be enforced **by the backend**.
The frontend may show or hide UI, but it must never be trusted to protect
these operations. Any frontend check is cosmetic.

---

## 1. Authentication

- Password hashing (bcrypt/argon2) is backend-only. The frontend never sees
  a password hash.
- Session tokens must be issued as **httpOnly, Secure, SameSite=Lax** cookies.
  Never returned to JavaScript.
- Any bearer-token fallback must use short expiry + refresh tokens with
  rotation. The frontend only receives access tokens with a lifespan of
  minutes, never persisted in `localStorage`.
- The mock `sessionToken` write in `authStore.js` is **development-only**.
  Delete it when switching to the real backend.

## 2. Authorization

Every route guarded by `RequireRole`, `RequireOrganizer`, `RequireScanner`,
or `RequireAdmin` in the frontend must have a **matching backend check**. The
frontend guard exists to avoid rendering pages a user obviously cannot use;
it is not a security boundary.

Specifically:

- Organizer endpoints must verify the caller is the owner of the target event.
- Scanner endpoints must verify the caller has an ACTIVE `ScannerAssignment`
  for the requested event. Scanner permission is **event-scoped**.
- Admin endpoints must verify the caller has the `SUPER_ADMIN` role.
- Customer endpoints must verify the caller owns the target ticket/order.

## 3. Payment verification

- The frontend **never** marks an order as paid. Doing so is a critical bug.
- The frontend **never** issues tickets. Only the backend, after verifying the
  provider webhook, issues tickets.
- The webhook handler must:
  1. Verify the signature with the provider's secret.
  2. Independently verify the transaction with the provider's API.
  3. Compare the amount to the expected order total before marking it paid.
  4. Be **idempotent**: repeated webhooks must be no-ops.
- The status polling endpoint must **never** return tickets until
  `orderStatus === "FULFILLED"`.

## 4. Ticket issuance

- Every admission receives its own `Ticket` row.
- `verificationToken` is generated by the backend using a cryptographically
  secure random source (or signed payload). It must be unguessable.
- The QR payload is **only** the `verificationToken`. Never encode user IDs,
  event IDs, or ticket type IDs into the QR code.
- The frontend never decides a ticket is valid. It renders what the backend
  returns from `/me/tickets` and from `/scanner/.../redeem`.

## 5. QR redemption

This is the most security-sensitive operation in the platform. The backend
MUST implement it atomically.

Pseudo-code (PostgreSQL example):

```sql
UPDATE tickets
SET status = 'CHECKED_IN',
    checked_in_at = NOW(),
    checked_in_by_scanner_id = $2
WHERE id = (SELECT id FROM tickets WHERE verification_token = $1)
  AND event_id = $3
  AND status = 'VALID'
RETURNING *;
